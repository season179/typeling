Typeling playback architecture

Story audio, word by word.

This page explains the six pieces needed for a proper end-of-session story player: audio narration, exact word highlighting, and a story pane that stays aligned while the child listens.

The six points

  1. 1Generate word timings from audio plus exact text.
  2. 2Tokenize the displayed story into stable word indexes.
  3. 3Serve audio and timings through the episode API.
  4. 4Build the story playback component.
  5. 5Lock manual scrolling while narration is active.
  6. 6Unlock and reset cleanly on pause, stop, or end.

The guiding rule: the audio clock drives the highlight, and the highlight drives the scroll.

Verdict

Use Qwen3-ForcedAligner for Typeling if the one-chapter spike passes quality checks. It fits the product contract because alignment is an offline artifact-generation step, not a kid-facing runtime dependency.

The official qwen-asr and vLLM docs are CUDA/NVIDIA-shaped: examples use device_map="cuda:0", bfloat16, FlashAttention, CUDA 12.9 wheels, and Docker with --gpus all. This Mac has no NVIDIA CUDA GPU, so do not spend time forcing that route locally.

The model is small enough to store and test here: the official Hugging Face repo is about 1.84 GB, and a third-party 4-bit MLX forced-aligner variant is about 979 MB. With 24 GB memory and 34 GiB free disk, this machine should support a careful Apple Silicon prototype.

The concrete next step is to run MLX-based Qwen alignment against data/audio/zack-s1-e0.wav, compare the returned words with Typeling's deterministic tokenizer, and accept Qwen only if the normalized output can become the same .words.json sidecar a managed API would produce.

Chosen setup path

Set up Qwen through the speech CLI, not LM Studio.

LM Studio is the wrong tool for this job because Typeling needs forced alignment: audio plus exact transcript in, word timestamps out. The local setup should install an Apple Silicon speech runner, smoke-test one chapter, and only then wrap the result as a Typeling sidecar generator.

Local tool boundary

  1. Keep Qwen outside the app runtime. It is a local media tool, not a Hono or React dependency.
  2. Use Soniqo's speech CLI on Apple Silicon. It runs models locally with MLX/CoreML and downloads model weights on first use.
  3. Start with aufklarer/Qwen3-ForcedAligner-0.6B-4bit. Move to the 8-bit variant only if the one-chapter quality check fails.
  4. Do not add Python, CUDA, vLLM, or LM Studio to Typeling for this spike.

Align Zack chapter 1

speech align data/audio/zack-s1-e0.wav \
  --text "$(cat data/audio/zack-s1-e0-source.txt)" \
  --language en \
  --aligner-model aufklarer/Qwen3-ForcedAligner-0.6B-4bit \
  | tee data/audio/zack-s1-e0.qwen-align.raw.txt

The first run may spend time downloading the aligner into the local model cache. No API key should be needed for this smoke test.

Acceptance gate

  1. The command writes non-empty raw output with one timestamped line per spoken word.
  2. The first and last words match the source text, and the total word count matches the 202-word source.
  3. Each timestamp is monotonic, non-negative, and inside the 101.24 second WAV duration.
  4. If the raw output is wrong, fix alignment setup first. Do not build the API or playback UI on guessed timings.

Fallbacks

  1. If the 4-bit model jitters, retry with aufklarer/Qwen3-ForcedAligner-0.6B-8bit.
  2. If leading silence causes the first word to start at zero incorrectly, trim the leading non-speech or run a VAD pre-pass before alignment.
  3. Use the official qwen-asr Python package only on a CUDA/NVIDIA machine or remote box. It is the canonical implementation, but not the practical local Mac path.

Write the sidecar

bun run audio:zack-s1-e0:timings

This Bun wrapper parses zack-s1-e0.qwen-align.raw.txt, compares it against Typeling's deterministic story tokenizer, and writes data/audio/zack-s1-e0.words.json with audio and text hashes.

The stable Typeling contract is: episode text + generated WAV -> validated word timing sidecar.

1

Derived artifact

Generate a word timing sidecar.

Layman's explanation

Think of this as making a tiny treasure map for the narration. The audio says the story out loud, and the timing file says: this word is heard here, the next word is heard there.

Typeling should not guess those times. It should take the real audio and the real story text, then ask a forced alignment tool to match them together.

Technical explanation

Add a script that reads the exact episode text and the generated WAV, submits both to a forced aligner, normalizes the response, and writes data/audio/<season>-e<idx>.words.json.

Input seasons/*.json episode text plus data/audio/*.wav.
Output Word records with index, text, start, and end.
Failure mode Hard fail when words are missing, reordered, duplicated wrongly, or timing moves backwards. 
{
  "seasonSlug": "zack-s1",
  "episodeIdx": 0,
  "audioPath": "data/audio/zack-s1-e0.wav",
  "words": [
    { "index": 0, "text": "In", "start": 0.18, "end": 0.32 },
    { "index": 1, "text": "a", "start": 0.32, "end": 0.39 }
  ]
}
2

Display contract

Tokenize the story into stable word indexes.

Layman's explanation

The page needs to know which visible word is word number 1, word number 2, word number 3, and so on. Spaces, commas, quotes, and line breaks should still look normal, but the actual words need number tags.

That way, when the timing file says word 58 is being read, the page can highlight exactly word 58.

Technical explanation

Add a deterministic tokenizer such as src/lib/storyWordTokens.ts. It should split text into render tokens while preserving the original text byte-for-byte when joined back together.

  • Word tokens get wordIndex.
  • Whitespace, punctuation, and newlines remain separate display tokens.
  • Contractions and hyphenated story words need an explicit rule.
  • Tests should cover quotes, punctuation, newlines, and repeated words.
type StoryToken =
  | { kind: "word"; text: string; wordIndex: number }
  | { kind: "space" | "punctuation" | "newline"; text: string };
3

Access boundary

Serve audio and timings through the episode API.

Layman's explanation

The browser should not rummage around in files. It should ask Typeling: "Can this child listen to this chapter?" If yes, Typeling sends back the audio and the word map.

This keeps locked chapters locked and keeps the playback feature tied to the same chapter rules as reading and typing.

Technical explanation

Add a route like GET /api/children/:id/episodes/:episodeIdx/audio. It should reuse the existing episode access check, then return a small JSON payload pointing at the audio asset and embedding or linking the alignment data.

200 Audio exists, alignment exists, and the episode is open for that child.
404 No audio/alignment artifact exists for that episode yet.
409/403 The chapter is stale, locked, or not available to that child.
4

Player surface

Build the story playback component.

Layman's explanation

This is the actual "listen to the story" screen. It shows the story, plays the voice, and lights up the word currently being spoken.

The child should experience it like a parent tracing a finger across the page while reading aloud.

Technical explanation

Refactor the current story reader into a component with an <audio> element, active playback state, rendered word spans, and a loop that reads audio.currentTime.

  • Use binary search over alignment words to find the active word.
  • Use requestAnimationFrame while playing for smooth highlighting.
  • Use media events for loading, pause, ended, error, and seek handling.
  • Keep native autoplay restrictions in mind: playback starts from a user action.
5

Alignment protection

Lock manual scrolling while narration is active.

Layman's explanation

While the voice is reading, the page should gently take the steering wheel. If the child scrolls away, the highlighted word may no longer be visible, and the story feels broken.

So during narration, Typeling should keep the current word in view and ignore manual scroll attempts.

Technical explanation

When isNarrating is true, apply a locked class to the story container and prevent user scroll inputs such as wheel, touchmove, and scroll-key behavior inside the reader.

  • Programmatic scroll remains allowed.
  • The active word calls scrollIntoView({ block: "center", inline: "nearest" }).
  • Use overscroll-behavior to avoid scroll chaining into the page.
  • Do not hide focus or trap keyboard navigation outside the player controls.
6

State release

Unlock cleanly on pause, stop, seek, or end.

Layman's explanation

When the story stops reading aloud, the page should become a normal story page again. The child can scroll, reread, or tap play again.

This makes the lock feel helpful instead of bossy.

Technical explanation

Model playback state explicitly. The scroll lock is derived from state === "playing", not from whether the component happens to have audio metadata loaded.

Playing Highlight active word, auto-scroll it into view, lock manual scroll.
Paused Keep current highlight if useful, stop animation loop, unlock manual scroll.
Ended Clear or settle highlight, stop animation loop, unlock scroll, show replay affordance.

Definition of done

Alignment quality

The generated word JSON validates against the exact displayed tokenizer output, with monotonic timestamps and no silent word mismatch.

Runtime behavior

Play starts from a user action, highlights track audio time, and seeking or replay recomputes the active word.

Scroll behavior

Manual scrolling is disabled only while the narration is actively playing. It returns immediately on pause, stop, or end.

Kid-facing fallback

If audio or alignment is missing, the chapter still displays as a readable story instead of becoming an error screen.
